新增第四个支付 provider（stripe / creem / paypal / waffo），定位为可选渠道，不改默认 provider。

### 关键事实（与官方 skill 文档的差异，均已用 SDK 类型定义核实）

- 官方 skill 文档（docs.waffo.ai/integrate/skill）**已过时**：
  - `createSession` **没有** `productType` 字段（商品类型由商品本身决定）
  - 没有 `client.webhooks.verify<T>()`，真实导出是独立函数 `verifyWebhook(body, sig, opts)`
  - 文档漏了 `subscription.renewed` / `recovered` / `plan_change_*` 等事件
  - `WebhookEventData.amount` 是 **display string**（如 "9.99"），不是 number
- `createSession` **没有 `cancelUrl` 参数** → 本项目 checkout 的取消回调链路对 Waffo 不适用
- `createSession` 返回的 `cs_<uuid>` **无法反查**（无 REST/GraphQL 入口），
  唯一可反查的业务键是我们自己传的 `orderMerchantExternalId`
- SDK 内部 `import { createSign, createPrivateKey } from "crypto"`（Node 专有，非 WebCrypto）。
  **已确认可在 CF Workers 跑**：nodejs_compat 下 node:crypto 全量可用（CF 2025-04-08 changelog）
- GraphQL 是 query-only；`payments(filter: { orderMerchantExternalId: { eq: $ref } })` 是文档明确给出的反查方式
- Waffo 金额用 display string（"9.99"），本项目存 minor units（990），边界必须显式换算（JPY 等零小数币种除外）

### 架构落点

- `src/extensions/payment/waffo.ts`：WaffoProvider（createPayment / getPaymentSession / getPaymentEvent / cancelSubscription；无 getPaymentBilling——Waffo 无客户门户，接口是 optional，页面已兜底）

## 事故：双 dev server 并存导致 .next 损坏（22:10 报错，已修复）

**报错**：`Cannot find module '../chunks/ssr/[turbopack]_runtime.js'`
（require 栈：`.next/server/pages/_document.js` → next/dist/build/utils.js）

**根因**：两个 `next dev` 进程同时写同一个 `.next` 目录，互相覆盖 chunk：

| PID | 启动 | 命令 | 绑定 |
|---|---|---|---|
| 18231/18238 | Tue 10/6 11:19 | `next dev --turbopack -H localhost -p 3000` | `[::1]:3000` |
| 36511/36517 | Thu 10/8 22:10 | `pnpm dev`（默认） | `*:3000` |

2026-10-08 现场证据：
- `_document.js` require 的 `[turbopack]_runtime.js` 在磁盘上**不存在**
- 同目录存在 4 个不同 hash 的 `[root-of-the-server]__*.js`（015a4b34 / 794de5af / d6847c98 / fa248b9f）
  → 至少 4 个构建代际的产物混在一起
- `.next/BUILD_ID` 是 Oct 6 12:51 的，但 `app-build-manifest.json` 是 Oct 8 22:10 的（缝合怪目录）

**修复**：kill 两个进程树（含 `.next/postcss.js` 子进程）→ `rm -rf .next`（1.9G）→ 重启单个 `pnpm dev`
→ 首页 200、`[turbopack]_runtime.js` 重新生成（28476 B）。
冒烟：`/` `/pricing` `/examples` `/create` = 200；`/admin/settings` = 307（未登录，预期）；
`/api/payment/notify/waffo` = 405（GET 不允许，路由存在，预期）。

**预防**：启 dev 前先 `lsof -nP -iTCP:3000 -sTCP:LISTEN`；一个项目只允许一个 dev server 实例。
macOS 上 `[::1]:3000`(IPv6 loopback) 与 `*:3000`(IPv6 wildcard) 因 SO_REUSEADDR **可以同时 bind 成功**，
所以端口不冲突≠只有一个实例——这是本次能悄悄并存 2 天的原因。

**顺带发现（未修，非阻塞）**：dev 启动警告 Next 推断的 workspace root 是 `/Users/xumingyue/`
（因为家目录存在 `/Users/xumingyue/pnpm-lock.yaml`），而非项目目录。想消除可设 `turbopack.root`。
另有 2 个 `next.config.mjs` 无效键警告：`experimental.turbopackFileSystemCacheForDev`、`reactCompiler`。

## 事故：/admin 登录后被弹回 sign-in（22:24 报错，已修复）

**症状**：登录返回 200，但访问 /admin 又回 sign-in，反复登录无效。
**真因**：不是认证 bug，是 **dev 下数据库连接走了 Hyperdrive 模拟分支**。

### 因果链（均有实测证据）

1. `next.config.mjs` 末尾调用 `initOpenNextCloudflareForDev()`；`wrangler.toml` 里有 `[[hyperdrive]]` 绑定
   → `next dev` 里 `getCloudflareContext().env.HYPERDRIVE` 存在 → `resolvePostgresConnection()` 返回
   `isHyperdrive = true`。
2. OpenNext 在 dev 走 `inNodejsRuntime` 分支，用 `addCloudflareContextToNodejsGlobal()` 把 CF context
   **挂到 globalThis 上只设置一次** → `getCloudflareContext()` 每次返回**同一个进程级对象**。
3. `getPostgresDb()` 的 Hyperdrive 分支用 `requestConnections`（WeakMap，key = CF context）做「每请求一条
   连接」缓存 → 在 dev 里退化成**进程级长连接**，正是 `postgres.ts` 注释里警告的「socket 被对端关掉后
   下一条查询一直挂着」场景。
4. 连接建立本身要 **1.4–6.4 s**（国内→东京 Supabase + Clash TUN 代理），僵尸 socket 则直接挂到超时。
5. `getSignUser()` 有 `SESSION_LOOKUP_TIMEOUT_MS = 10000`，超时被 catch 成 `return null`；
   `requireAdminAccess` 见 user 为空 → `redirect('/sign-in')`。于是**永远登不进去**。

### 关键证据

- `POST /api/auth/sign-in/email` → **200**；`wedding-crest.session` 里确实写入了 `live=true` 的新会话
  （schema 是 `wedding-crest` 不是 public！这个 Supabase 是**多项目共用**：
  nailshapes / roofcast / tokirei / watermark / wedding-crest / public）
- `/admin` 稳定 **307 + 10.4–13.6 s**，与 10s 超时完全吻合；期间出现过一次 `GET /admin 200 in 3118ms`
  （socket 恰好新鲜）
- 直连库：冷连接 1.36–6.36 s，热查询 120–400 ms
- 把 Hyperdrive 绑定临时注释掉重启 → `/admin` 从 10.4 s 降到 **0.137–0.178 s**（证明分支是元凶）
- 恢复绑定 + 打补丁 → `/admin` 第 2 次起 **0.157–0.164 s**

### 修复（1 行）

`src/core/db/postgres.ts`：`if (isHyperdrive || NODE_ENV==='production')`
→ `if (isProd || (isHyperdrive && isCloudflareWorker))`。
dev 下回落到项目本来已配置的池化单例（`.env.local` 的 `DB_SINGLETON_ENABLED=true`、
`DB_MAX_CONNECTIONS=10`）；生产/真 Worker 行为完全不变（`isProd` 为真仍进原分支）。

### 端到端验证方法（可复用，很有用）

要证明「cookie 有效 / 会话可读」，必须用**真实签名的 cookie**。要点：
- cookie 名：`better-auth.session_token`
- 值：`<session.token>.<signature>`，签名为 **base64 标准编码且带 padding（必须 44 字符、以 `=` 结尾）**。
  用 `crypto.createHmac('sha256', AUTH_SECRET).update(token).digest('base64')`。
  **踩坑：用 `.digest('base64url')` 得到 43 字符无 padding，better-call 直接判 null**（见
  `better-call/dist/index.js` 的 `signature.length !== 44 || !signature.endsWith('=')`）。
- 验证：`GET /api/auth/get-session` 带该 cookie 应返回 session+user；随后 `/admin` 会
  307 → `/admin/users`（后台默认页），**不再是 `/sign-in`**。
- DB 里的 `config.auth_secret` 与 `.env.local` 的 `AUTH_SECRET` 一致（已核对 sha256），排除密钥分裂。

### 别的坑

- `/admin/settings` 返回 404 是**正常的**：项目里没有这个路由，设置页在顶层 `/settings`。
- 这个 Supabase 是多项目共用，`public` schema 里也有同名表，**排查时务必先确认 `DB_SCHEMA`**，
  否则会像我第一次那样看错表得出错误结论。
