## 修复：创建项目时 wedding_project_element 写入失败（~25% 项目元素行丢失）

**现象**：`200 OK: Failed query: insert into "wedding-crest"."wedding_project_element" ...`
（HTTP 200 + 错误体，是 respErr 的老行为，错误本身是 drizzle 包装后的 "Failed query"，真实原因在 error.cause）

**线上数据证据**（只读查询）：
- 47 个项目中 **12 个 elements=0**（25%），最早可追到 2026-08-20；其中部分还有 generation → 用户拿到的是丢失花艺/边框/样例的结果
- `example_image/example_match/example_style` 三种类型都能写入（15 个项目有），所以**不是新类型的问题**

**排除**：无 CHECK 约束、无 RLS、无 policy、无 trigger；用完全相同 5 行参数在事务里复现 → **插入成功**。所以不是 schema/约束问题，是连接层瞬时失败。

**真因**：`db()` → `getPostgresDb()` 在生产（Hyperdrive / NODE_ENV=production）**每次调用都新建一个 postgres.js client（max:1, connect_timeout:5）**，
而 `createWeddingProject` 连续调用 3 次 db()（插项目 / 插元素 / 读回）。三条语句 = 三条独立 TCP 连接且**不在事务里**，
第二条失败时第一条已提交 → 项目留下、元素全丢。客户端也从不 close（注释说用 ctx.waitUntil 但代码里没有）。
线上 max_connections=60、当前仅 14，所以不是连接耗尽，是 Hyperdrive/链路瞬时失败。

**修复**：
1. 新增 `src/core/db/transaction.ts`：`runInDbTransaction()`（postgres 走独立 client + BEGIN/COMMIT/ROLLBACK + finally close；其他 provider 退化为 db()）、
   `withDbRetry()`、`isTransientDbError()`（SQLSTATE + node code 白/黑名单，区分「连接掉了」与「约束拒绝」）、`describeDbError()`（打 SQLSTATE/detail/constraint）
2. `src/core/db/postgres.ts`：抽出 `resolvePostgresConnection()` + `createPostgresClient()`，保证事务用的 client 与请求链路同参数（Hyperdrive 优先、search_path、no_prepare）
3. `createWeddingProject`：项目 + 元素 + 读回**全部在一个事务一条连接上**；写入幂等（`onConflictDoNothing` + 先删该 project 的元素），所以重试不会产生重复行；失败打 SQLSTATE
4. 同类隐患一并修：`updateWeddingProjectElements`（先删后插）、`saveWeddingAssets`（先删后插）同样收进事务 + 重试
5. `getWeddingProject` 重构为 `loadWeddingProject(exec, id)`，供事务内复用同一连接读回

**验证**：
- 回滚测试：事务内插项目后故意触发 FK 违规 → `rows_left=0`（修复前该行会留下）
- 创建测试：返回 6 条元素（2 flower + frame + example_image/match/style），input 解析正确；测试数据已清理
- 分类测试：57P01/53300/CONNECT_TIMEOUT/ECONNRESET → 重试；23505/FK/42703 → 不重试；瞬时错误重试 1 次后成功
- tsc / eslint / next build 全过

**遗留**：`respErr` 仍返回 HTTP 200（错误被当成成功），前端 toast 才会显示 "200 OK: Failed query"；另外每次 db() 仍各开一条连接（本次只在写入路径收敛），读写链路整体改 per-request 复用是下一步。

## 修复：admin 改了 example 图后首页一直显示旧图（浏览器缓存）

**根因**：首页 example 图是客户端 fetch `/api/wedding/examples?surface=home`，两层缓存叠加：
1. 接口 Cache-Control 原为 `max-age=300, s-maxage=3600, SWR=86400`（SWR 24h 内可回旧响应）
2. `wedding-examples-provider.tsx` 用 `cache: 'force-cache'` —— 该模式**过期也直接用缓存、不发请求**，对回访浏览器近乎永久旧图（需硬刷新）。Cloudflare 边缘没实际缓存（无 cf-cache-status，API 路径默认不进边缘缓存），主因是浏览器侧。
次因：`listWeddingExamplesSafe` 2500ms 超时回退 `home-examples.ts` 硬编码旧图（偶发）。

**修复**（commit `c79ea51`，Version ID `f9764823-1a6b-4e92-929c-e32225fde2a6`）：
- provider fetch 改 `cache: 'no-cache'`（每次协商校验，304 不耗流量）
- Cache-Control 改 `max-age=60, s-maxage=600, SWR=3600`，admin 改完约 1 分钟内生效

**线上验证**：新 Cache-Control 已生效；接口返回的 "Minimal Line Art Wedding Crest" 已是 DB 里的新图 `af80a9fc06a4ee6a88f6ad4339da57a5.webp`（硬编码兜底里是旧的 `d1a4c21b...`），证明 admin 的修改在库里、新接口数据正确。
